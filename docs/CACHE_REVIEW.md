## LXServer 实际如何工作

1. 网页端在允许使用服务端缓存时，先检查已有服务端音频文件，再读本地链接缓存，最后请求解析。直接调用 /api/music/url 并不等于执行了网页完整流程。客户端目前缺少服务端文件缓存查询。
2. checkCache 按用户、歌曲 ID、音质查索引，并检查文件存在。优先同音质下载文件、同音质缓存文件；非 exactQuality 模式允许其他音质兜底，并返回实际 quality。名称碰撞单独标记 isCollision，不能盲目当成同一首歌。
3. 服务端文件缓存按配置进行容量、保留时长清理；不是播放地址 5 分钟后就删除音频。网页的链接缓存存于 localStorage，该读取路径未体现固定 5 分钟 TTL，重试时绕过链接缓存。
4. 解析阶段服务端会尝试多个同平台自定义源；如果返回 URL 后才加载失败，网页记录失败 sourceName/sourceId，携带 excludeApiSources 请求其他源，再考虑降级。客户端当前只有降级，没有加载失败后的源排除，可能反复得到同一个坏链接。
5. quality/size 可对单个档位做解析和远程大小探测，网页缓存成功探测，失败删除探测记录。它不是一次返回全部可播放档位的接口，也不等于对编码、位深的独立鉴定。内部 resolveServerSong 即使不允许音质降级，也可能搜索其他平台候选，不能不加审查地用于“严格同平台可用性”判断。
6. 自定义解析返回的 type 可能直接取请求的 quality，标签不能视为对实际文件的独立检测证明。

## 当前客户端需要调整的地方

| 当前策略 | 审查结论 |
| --- | --- |
| 成功档位固定记 6 小时并排第一 | 只能算快速恢复提示，不应压过后续已知的更高可用音质；首次临时失败可能使用户长期停在低档 |
| 所有失败统一抑制 2 分钟 | 混淆网络超时、坏地址、解码失败和源确实不支持；不应全部持久化为歌曲档位不可用 |
| 地址固定 5 分钟 | 是保守工程参数，不是服务端契约或行业标准；有可靠有效期时应采用，未知时靠失效恢复与保守上限 |
| 请求成功后直接加载，失败降档 | 应先尝试同档位其他解析源，保留失败源信息，且限定单次恢复次数与总耗时 |
| 仅使用客户端链接/结果缓存 | 缺少服务端已缓存文件，导致明明服务端有文件仍去解析 |
| 新搜索元数据当完整列表 | 新鲜不等于完整；需按平台字段明确程度识别，未知和平台占位条目不能作为“不支持”的证据 |
| 安全存储整份播放历史 | 复用依赖便于首版实现，但普通策略记录不需要凭据级存储；后续应与会话凭据分离 |

## 建议的下一版流程（尚未实现）

按当前首选和可信元数据确定目标档位 → 检查同档位本机音频文件（现已实现）/服务端文件 → 有效链接 → 同平台解析 → URL 加载失败时排除该解析源并尝试其他源 → 耗尽后按允许档位降级。

- 网络整体不可用时停止逐档解析，保留重试；认证失败回登录。未分类的 500 不能直接判成该档永久不存在。
- 近期成功档位可用于快速恢复，但不是新的偏好上限；失败短期退避主要放在会话内，只有明确能力信息才作为更长期约束。
- 存储文件需要稳定歌曲/音质身份，不以可能过期的 URL 作为唯一身份；同名歌曲不同平台与版本不自动合并。
- 普通边播边缓存按容量淘汰，用户主动下载单独管理；文件缓存与 URL TTL 不混为一谈。
- 只读取、播放已有服务端缓存；自动触发服务端下载、升级缓存须另行明确产品范围，不在本次审查中启用。

优先修复顺序：服务端已有缓存读取与鉴权 → 同档位失败源排除 → 错误分类和恢复预算 → 重新评估结果缓存 → 本机音频字节缓存。暂不继续扩大固定 TTL 状态机。

## 本次落地范围

已接入精确音质的服务端已有文件查询、同档位失败源排除、解析次数/耗时预算、基础错误分类；失败记录仅内存 30 秒。D009 按用户最终要求改为长期沿用与首选绑定的歌曲成功档位，不按时钟重新探测；修改首选/主动重试/原档失败才重新选择，并保留作用域与容量清理。此点修订了上述初始建议。新鲜列表含平台占位项时不视为完整能力清单。

手机音频字节缓存与主动下载已在后续实现，详见 [LOCAL_MEDIA.md](LOCAL_MEDIA.md)。当前使用文件与 JSON 索引，未引入独立数据库；未实现服务端自动下载/升级。真实音源编码、错误细分与真实文件有效期仍需部署实测。
